✓ 安全保证 · Phase C 严格保留 L3 弃用时确立的 byte-exact 不变量: 一个 chunk 仅在 byte_start/byte_end 与 pool entry 完全对齐时才复用。 没有 MiniLM cos similarity 兜底、没有 ±N token 容差、没有 whitespace-tolerance。 这正是 8.2% byte-drift 案例被故意拒绝的设计意图 — 那些是变量改名、签名变更等 L3 误判但 byte 不一致的情况,chunk 层应该坚持不放行。

Phase C 读路径决策流程

1 _try_placeholder_chunk_lossy_match (入口)
从 match_prefix 调用。检查 SGLANG_CHUNKED_PLACEHOLDER_KNN_MATCH=1 开关,默认 OFF(生产安全)。 校验 req 有 placeholder_anchor_token_spans。
2 _build_chunk_plan (决策)
遍历每个 span → ASTChunker.chunk_text(Phase A) → 按 (slot_id, chunk_signature) 查 pool → _find_byte_exact_chunk_entry 严格 byte-exact 校验 → 生成 ChunkDecision 列表(action: copy_pool | dense_prefill)。
3 _find_byte_exact_chunk_entry (严格校验)
返回首个满足 byte_start == chunk.byte_start AND byte_end == chunk.byte_end 的 entry。 无容差 · 无 MiniLM。
4 _execute_chunk_plan (执行)
对每个 copy_pool 决策: alloc → move_kv_cache → _apply_rope_delta_to_head(head_tokens=2) → append to value list。 OOM 时自动 fallback 到 dense prefill(skip_reason = "alloc_failed")。
5 match_prefix 透传
把新分配的 slots 通过 torch.cat 拼接到 match_result.device_indices。 下游 Req.init_next_round_input_ids(schedule_batch.py:997)消费透明 — prefill kernel 把这些 slots 当作已缓存 prefix,跳过对应 token 的计算。

Phase D — Telemetry 计数器

计数器 触发时机 用途
placeholder_chunk_pool_hit_count 每次成功从 pool copy 一个 chunk 总命中数,反映 L4 chunk 复用频率
placeholder_chunk_pool_miss_count 每次 dense_prefill 决策 总未命中数
placeholder_chunk_pool_skip_no_entry_count pool 为空,或 (slot_id, sig) 无 entry Phase A/B 写路径覆盖率指标
placeholder_chunk_pool_skip_byte_drift_count pool entry 的 byte 范围与 chunk 不一致 指示是否需要 Phase E 容差策略
placeholder_chunk_pool_skip_size_mismatch_count byte 范围对齐但 token 长度不同 chunker 漂移检测器
placeholder_chunk_pool_skip_alloc_failed_count KV 分配失败(OOM) 显存压力指标
placeholder_chunk_pool_rope_ops_count 每次 head-only RoPE 旋转(head_tokens=2/copy) RoPE 计算开销
placeholder_chunk_pool_total_tokens_reused 累计从 pool 复用的 token 数 实际节省的 prefill token 数
placeholder_chunk_pool_total_tokens_dense 累计 dense 计算的 token 数 剩余 prefill 工作量

所有计数器在 RadixCache 实例上,进程级累计。 Binary confidence policy:每个 ChunkDecision.confidence ∈ {0.0, 1.0}, 无分数置信度。
