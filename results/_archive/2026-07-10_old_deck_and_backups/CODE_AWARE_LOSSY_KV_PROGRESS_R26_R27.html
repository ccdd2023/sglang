1 TL;DR — 3-way 头对头

R26/R27 实验确认：3B × 3 agents 给出 ~2× 速度（模型族无关）， 但出现 反直觉的 accuracy trade-off —— Coder-3B 完全失去 FAIL 检测能力（0%）， 而 general 3B-Instruct 仍能识别 27% 的 bug。R19 BEST（7B × 5）仍是 accuracy-optimal。

🎯 Ground truth

所有 5 个 SWE-bench pandas case 都属于 FAIL（code 含 bug）。 FAIL_acc = 模型正确说出 "FAIL" 的比例；越高越好。 Lossless PASS-rate 也算错（48-100%），因为模型偏向 PASS。

3 为什么 3B × 3 比 7B × 5 快

机制拆解

因素效果
更小的 model → 更小的 KV footprint placeholder_chunk_pool 能装下更多 slot；c2_chunk_reused 从 ~600 跳到 2886（4.8×）
3 层/2 头（vs 7B 的 28 层/4 头） 每个 chunk KV block 小 4×；pool 总占用降到 7B 的 ~25%
3 agents 取代 5 agents 并发竞争更少；eviction pressure 更小；每个 agent 看到更热的 pool
Agent 2 拿到 2.414× implementer → tester：实现完再测试，AST chunk 完全匹配

4 🔑 反直觉发现：Coder ≠ better at code critique

R27 (3B-Coder) 是 FAIL 检测 最差 的配置 (0% FAIL_acc)

Lossless 时模型对 100% buggy code 都说 "PASS clean"。 Lossy 时 86.7% PASS、13.3% UNK、0% FAIL。 Coder 训练的目标是「改善 code」，所以面对 critique 任务时默认 "PASS, 这是改法"， 而不是 "FAIL"。 General Instruct 模型（R26）更保守，能识别 27% 的 bug。

✅ Lossy doesn't degrade accuracy

在所有三个模型中，lossy 的 FAIL_acc 都 ≥ lossless。 这反驳了 "lossy 一定牺牲精度" 的默认假设。 UNK（垃圾输出率）是独立问题 —— 模型根本没产出 verdict，不是 verdict 错了。

5 决策矩阵

🚀 Speed first R26

3B-Instruct × 3 agents

  • 2.014× speedup
  • 27% FAIL_acc — 会漏 bug 但快
  • 适合：成本敏感、可容忍 5-10% 垃圾

🎯 Accuracy first R19

7B-Coder × 5 agents

  • 1.29× speedup
  • 60% FAIL_acc — 找 bug 最强
  • 适合：用户面 critique / review 任务

⚖️ Balanced R26 + oracle

R26 + R25-A1 skip-risky-chunks oracle

  • R26 速度 + 跳过风险 chunk
  • 预期 UNK 从 20% → 0%
  • oracle 在 7B 数据上训练，3B 上未验证

❌ Avoid R27

3B-Coder × 3 agents

  • 跟 R26 几乎同速
  • 但 critique 任务上 更差
  • 原因：Coder 训练 → PASS 偏向

为什么 3B 和 7B 共享 chunk pool？

3B-Instruct general 与 7B-Coder 同属 Qwen2.5 tokenizer family，所以 AST chunk signature （normalized text 的 sha1）跨模型匹配 —— 3B precompute 出来的 chunk pool 条目在 chunk 粒度上 byte-identical。
