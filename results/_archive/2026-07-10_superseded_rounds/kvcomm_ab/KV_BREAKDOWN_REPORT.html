KV 复用分解：Prefix vs Suffix

sglang-kvflow · 大项目（giant-codebase / SWE-Smith）KVCOMM 位置旋转场景 · 7B-Coder · 2026-07-01

一句话结论

在这个大项目测试里，prefix（radix 同位置字节精确）KV 几乎为 0（~38 tokens，只有 system prompt）——因为每个 agent 用不同的 cache_salt，radix 树对 agent 2..N 是冷的（公平测量要求）。所有真正的复用都是 suffix（跨位置旋转拷贝）KV，量级只有 prompt 的 7%–19%（~500–1400 tokens / ~7000 tokens prompt）。复用量这么小，正是加速只有 1.0–1.14× 的直接原因：省下的 prefill 太少。

而且 per-case 方差极大：很多 case 复用 0，少数 case 命中 1000–1900 tokens——后者恰恰是 F1 崩到 0.00–0.06 的 case（cross-context KV loss）。

两个关键变换（构造 KVCOMM 场景）

position-shift 位置旋转（核心 KVCOMM 场景）

每个 agent 把 5 个 segment 的顺序循环移位 idx-1 位。内容字节完全相同，只是绝对位置不同。agent 1 = [s0,s1,s2,s3,s4]，agent 2 = [s1,s2,s3,s4,s0]，… 这正是 KVCOMM 描述的"相同 prompt 在不同位置"。

partial-share 部分共享（让 AST 粒度有优势的场景）

每个 agent 丢掉一个不同的顶层函数（defs[(idx-1) % len(defs)]）。这样 segment 文本各 agent 不同（whole-slot 字节精确匹配失败），但剩下的函数仍字节相同（AST 按函数粒度仍能跨位置复用）。

公平性保证：每个 agent 的 cache_salt = giant:{case}:{seg_count}:{max_chars}:{agent_count}:{mode}:{idx} 各不相同 → agent 2..N 的 radix 树是冷的 → 共享代码只能通过 KVCOMM 旋转拷贝路径恢复，不能用 radix prefix 白嫖。这正是 radix_prefix_tokens ≈ 38（只有 system prompt）的原因。

agent 1（implementer）是 source：它先跑、把代码 KV 存进 pool；agent 2–5 是 reuser，从 pool 里跨位置拷贝。所有统计排除 agent 1。

读图要点：
  • PREFIX 永远 ≈ 38–42 tokens（紫色那一小条）——公平测量的 cache_salt 让 radix 对 reuser 是冷的，系统 prompt 之外没有白嫖的 prefix。
  • SUFFIX（绿色）才是真实复用，且只有 7–19% of prompt。full-share 下 L2≈L4（~1300 tok）；partial-share 下 L4 只有 516——因为 AST 只拷贝共享的函数，whole-slot 拷的是整个槽（含 import 大块）。
  • 剩余 80–92% 仍要真实 prefill——所以 TTFT 只能省下这 7–19% 对应的 prefill 时间，加速被天花板限制在 ~1.1×。

两个极端：
  • suffix=0：partial-share 下该 agent 丢的函数让 whole-slot 失配、且 AST 无共享函数命中（或 source 还没存）→ 零复用，退化为纯 prefill。
  • suffix=1000–1900：命中了大量共享函数 → 但这些 case 的 F1 恰恰崩到 0.00–0.06（cross-context KV loss：KV 在 layer>0 编码了它前面的 prefix，重排后 prefix 变了 → 拷过去的 KV 是 stale 的）。复用越多，越不准。
这是 KVCOMM raw-copy + RoPE 的根本张力：无损 gap 必须先 prefill（staged）→ 只有 chunk run 省下来 → 量小 → 加速小；想多复用 → cross-context loss → F1 崩。

⑤ 结论与下一步

问题答案
大项目有没有加速？有，但温和：L2 full-share 1.144×（7B 最好），partial-share 下仅 1.0–1.04×。
PREFIX KV 多大？~38–42 tokens（几乎为 0，radix 被故意搞冷）。
SUFFIX KV 多大？516–1399 tokens = prompt 的 7–19%。
理论上限多大？7222 tok = prompt 的 97.9%（full-share）/ 6840 tok = 92.8%（partial-share）。
利用率多少？仅 8–20%——80%+ 可复用 KV 没吃到（staged 只拷第一个 chunk run + 0 命中 case）。
为什么加速不大？不是没东西可复用（有 97.9%），而是机制只吃到 18%；且多复用会触发 cross-context loss（F1 崩）。
AST（L4）赢过通用 L2 了吗？没有。full-share 更慢；partial-share 12-task 鲁棒结果 L4/L2=0.96×（略慢），仅 accuracy 占优（F1 0.622 vs 0.513）。

剩余杠杆（按提升空间排序）

  • ① 提高 KV 利用率（最大空间）：当前只吃 8–20%，理论有 97.9%。staged 机制只拷第一个 contiguous chunk run → 改成多 run 全拷贝（每个共享函数/槽都拷，不只第一个连续段）+ 提命中率（source 预存、消除 0 命中 case）。利用率从 ~18% → 60%+ 是加速数量级提升的主路径。
  • ② 批量化 AST 拷贝：把 N 个 per-chunk alloc+move+RoPE 合成 1 次 → 消除 per-chunk overhead，让 L4 的复用真正转成速度优势（未实现，待确认）。
  • ③ 修 cross-context loss（解锁"多复用"的精度代价）：true CacheBlend attention-recompute（option C，贵）——不修这个，①提到 60%+ 时 F1 会崩（复用越多越不准）。这是上限能否落地的精度瓶颈。

⑥ MULTI_SLOT 突破：拷全部 5 槽（2026-07-01）

实施了杠杆 ① —— SGLANG_CACHEBLEND_MULTI_SLOT=1：stage leading instruction gap（真实 KV），然后把全部 5 个 code_base 槽在一次 batched alloc/move/RoPE 里拷贝，只置零 ~13-tok 的 inter-slot header（COMPACT=0，位置正确）。打破"只拷 1 槽"的天花板。

关键发现：复用越多 → 精度越崩（cross-context KV loss）

这是 c2-cacheblend-lossy-not-safe 的最终确认：raw-copy + RoPE 对大量跨上下文 KV 复用是 lossy 的。KV 在 layer>0 编码了它前面的 prefix；agent 2 的 prefix 不同（旋转顺序 + 不同 leading gap）→ 拷过去的 slot KV 是 stale 的。复用 1 槽（1400 tok）损失可控（F1 0.46）；复用 5 槽（7100 tok）损失毁灭性（F1 0.00）。置零的 ~52 tok header 不是主因 —— 7100 tok 的 stale slot KV 才是。

结论：MULTI_SLOT 解决了利用率/速度天花板，但加剧了精度问题。用户目标（好加速 + 可接受精度）未达成：multi-slot 给了 7.5× 速度但 F1=0。根本瓶颈是 cross-context KV loss，raw-copy+RoPE 无法修。唯一出路是 true CacheBlend（对拷贝的 chunk 在新 context 下重算 attention）—— option C，贵，是 c2-fundamental-limits 指出的已知路径。

剩余限制：KV pool OOM（已知）

MULTI_SLOT 每次拷 ~7160 tok（single-slot 的 5×）。paged allocator 的 alloc 满时返回 None 且不触发 radix 驱逐（allocator.py:170），所以跨 task 累积的 radix prefix 耗尽 pool → 后续 reuser alloc=NONE → 0 复用（17/32 未命中，拖高 aggregate 到 539ms）。

  • 已修：batched executor 的 cap 原本只算 copied chunks 不算 zeroed gaps → device_indices > input_len → flashinfer 崩溃（task 7）。改成 cap on total_new（gaps+chunks）。
  • 尝试但失败：① EVICT_ON_ALLOC（alloc 失败时 mid-match 触发驱逐）→ 崩溃（释放 in-use exact_node）。② graceful trailing-chunk drop（拷不下就少拷几槽）→ KV slot leak（runtime checker 检测到未记账 token）。两者均已回退。
  • 当前：warn-only mem check（SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_IDLE=0）让 run 不崩；leak 有界（pool 耗尽 → 0 复用，graceful，无损坏）。
  • 根因（待修）：MULTI_SLOT 拷贝的 span 偶尔没被正确 insert 进 radix tree（不可驱逐也不释放）→ leak。彻底修需要 ephemeral copy（拷贝 span 不持久化，用完即释放），是 prior ephemeral attempt 留下的已知难题。
