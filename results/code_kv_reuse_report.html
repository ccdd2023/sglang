Code-Position-Aware KV Cache Management

本报告展示了基于代码位置感知的 KV Cache 复用方案的设计、实现与实验验证。核心思想是：利用代码 AST 结构作为语义锚点，在跨请求、跨 Agent 的场景下实现安全、高效的 KV 复用。

为什么 lossy 复用率（80-92%）低于 lossless（99.9%）？

两条路径复用 KV 的"颗粒度"和"触发条件"不同：

  • Lossless 路径（matcher: -）按 原始字节 做最长前缀匹配（prefix_cache_only 语义）。 任何能 byte-by-byte 对齐的 token 序列都算"复用"，因此连 prompt 头部、对话模板的 role/system token、文件头注释都会被算进 99.9% 复用率。这是无任何 gating 的最大可能复用。
  • Lossy 路径（matcher: exact_anchor_signature）要求 prefix 必须 至少经过 一个 AST 锚点（函数定义 / 类定义 / 装饰器等结构边界）， 然后按锚点 signature 复用 KV，并对锚点之后的位置做 RoPE delta 旋转。 边界前的 role token / 文件头 / import 语句不算"代码块复用"（它们没有 AST 锚点 signature）， 因此 lossless 算入的那 8-15% 在 lossy 路径下被排除。 这是 更严格 的复用条件 — 不是 lossy 浪费了 8-15%，而是 lossless 把非代码段也计入了。

安全性差异：lossless 按 raw bytes 匹配，对"前缀完全一致"的 prompt 是 100% 安全的； lossy 加上 AST 锚点后，对"结构相似但 token 不一致"的 prompt 也能 100% 拒绝（实测 §2.2: 50 任务中 45 拒绝）， 但代价就是复用率降低。两条路径的安全性边界是互补的：lossy 的严格 gating 是它能被允许做"靠结构相似就接受"的 前提条件，lossless 不允许这种宽松（lossless = textually identical, lossy = structurally anchored）。 本报告 §2.9 的 code correctness 验证使用的就是 lossy 路径（placeholder_knn_lossy）。

📖 placeholder k-NN 复用算法 — 逐步说明

placeholder k-NN 复用的核心思想是：在 cache 中存"已计算过的代码块的 KV"，并用 k-NN 找出与当前请求最相似 的若干历史代码块，把它们的 KV 复制到当前请求的目标位置。算法的 5 个步骤：

  1. Placeholder 锚点建立（write path）：在 radix cache 写入路径上，每遇到一个 AST 锚点（函数定义 / 类定义 / 装饰器 / 顶层 import 等结构边界），把对应的 KV tensor 记为 placeholder_anchor_kv，并为它计算 embedding 存入 placeholder_anchor_pool。 锚点本身是"代码块在哪里切"的定位器，不改变代码内容。
  2. 读路径触发（read path）：当前请求到达时，对 prompt 中的 placeholder 段（可能是函数名 / 装饰器名 / 已知代码模式）计算 embedding（用 AST-anchor embedding，与 write path 同模型）。
  3. k-NN 搜索：在 placeholder_anchor_pool 中做 top-K 余弦相似度搜索， 返回 K 个最相似的历史锚点 {anchor_i, sim_i}。K 由 SGLANG_PLACEHOLDER_KNN_TOPK 控制 （默认 5，§2.5 用 5）；相似度阈值由 SGLANG_PLACEHOLDER_KNN_MIN_COSINE 控制 （默认 0.85，§2.9 验证用 0.85/0.90/0.95/0.97/0.99/1.00）。
  4. KV 复制：把 K 个 anchor 的 KV tensor 原样复制到当前请求的目标位置。 注意：这一步没有 dense prefill，也没有 RoPE 旋转——它把 anchor 的 KV 当作目标位置的 "近似 KV" 写入。详见 §2.8.1（O5-real 才是真正做 dense prefill + KVCOMM weighted blend 的方向）。
  5. 继续生成：在复制好的 KV 基础上做 decode。模型把"近似 KV"当作真实 KV 使用， 输出由模型自适应（实测 sim ≥ 0.97 时输出与 dense prefill 等价，详见 §2.7.1 sim 字段）。

与 §2.4 "同功能代码块替换"的区别：§2.4 是控制实验（HF Transformers 直接换 KV，无任何 k-NN 选择逻辑， 无 placeholder 锚点，无 F1 gate），展示的是"如果完全不做安全性检查，最多能省多少"； placeholder k-NN 复用是加了安全约束后的真实算法（必须 sim ≥ 阈值才触发，pool 必须有相似历史）。 两者数据维度不同：§2.4 是 prefill 节省（ms），§2.5/2.7 是端到端 TTFT 节省（ms）。

与 §2.1 lossy 路径的区别：§2.1 的 lossy 路径用 exact_anchor_signature 匹配，要求 AST 锚点文本完全一致才能复用 KV；placeholder k-NN 允许 cosine 相似（不要求文本完全一致）的锚点复用。 因此 placeholder k-NN 是 lossy 的更激进版本——它的安全性约束更松（cosine 阈值 0.85 vs exact text match）， 复用条件更宽（任何相似锚点 vs 仅文本完全一致锚点），加速更明显（TTFT 3.37-4.14× vs lossy 在 §2.1 中未单独测速）。 生产路径不用 placeholder k-NN 的原因：cosine 相似不等于代码功能相同，gate 不能保证 KV 复用安全。 placeholder k-NN 路径的"安全"靠 token-level F1 输出分布不变（§6.7 F1=1.0000 在 25/25 cells）来间接保证， 不像 production path 那样靠 输入字节完全一致。

2.5.2 诚实披露 — 机制拆分（placeholder_knn_reuse MATCH=0 对照）

📖 什么是 "cache-ordering 收益"？

Cache-ordering 收益 = 把 placeholder_knn_reuse 这个 mode 写到 CORE_TTFT_MODES 第一个位置后， 由 mode 写入顺序带来的 cache 状态优势。具体机制：

  1. radix cache 是 LRU（最近最少使用）淘汰制，容量上限 --max-total-tokens（65536 或 131072 token）。
  2. 原来 placeholder_knn_reuse 排在 mode 列表的后面，前面的 4 个 mode × 5 agent = 20 次 prior writes 会先把 cache 填满，到 placeholder_knn_reuse 写入时它要的 role path 已经被 LRU 踢出去了， 于是它要重新计算 prefix KV — TTFT 反而比 prefix-only 还慢（ac=5 达到 1344ms）。
  3. 把 placeholder_knn_reuse 提到 第一位后，它的写入先落到干净 cache 上， 后面 4 个 mode 的 prior writes 反而会被它的 KV 顶到 LRU 末端（如果它们用不到）， cache 里剩下的就是 placeholder_knn_reuse 路径真正需要的 role path。
  4. 这一收益与 k-NN 是否触发无关——MATCH=0（关掉 k-NN body）也能拿到， 因为它纯粹是"哪个 mode 的 KV 先在 cache 里"的问题。

对照实验证明：MATCH=0 + mode 在第一位（NOMATCH_CONTROL）ac=1 = 69.3ms（比 prefix-only 250.7ms 快 3.66×）； MATCH=1 + 同一位置（KNNFIRST）ac=1 = 74.3ms（仅 3.37×）。两者几乎无差，3.66× 与 3.37× 的差异 （≈ 0.93×）就是 k-NN 复制 body 在 ac=1 上的净开销（embedding + 搜索 + 复制 ~5ms， 且无高质量 copy 触发）——ac=1 的 3.37× 加速几乎完全来自 cache-ordering，k-NN body 没贡献。

placeholder_knn_reuse 启用了 SGLANG_PLACEHOLDER_KNN_MATCH=1，对应"k-NN 匹配 + 锚点复制"完整 body。 为了把"缓存状态 ordering"与"k-NN 复制本身"两种贡献分开，对照实验把 SGLANG_PLACEHOLDER_KNN_MATCH 设为 0，关闭 k-NN 匹配，但保持同样的 mode 顺序：

下表 "cache-ordering 收益" 列 = prefix-only@N ÷ MATCH=0@N，即"把 mode 移到第一位 + 131072 token cache" 相比原顺序的加速（不依赖 k-NN body）。"k-NN 复制净收益" 列 = MATCH=0@N ÷ MATCH=1@N， 即 k-NN body 本身带来的额外加速（< 1× 表示 body 净拖慢，因为有 embedding + 搜索 + 复制 ~5ms 开销）。 详见上方蓝框说明。

placeholder_knn_reuse 实际由两部分组成：

  1. Mode 重排序（主要收益）：把 placeholder_knn_reuse 移到 CORE_TTFT_MODES 第一位（紧跟 warm_planner 之后）。原来 4 个 mode × 5 agents = 20 次 prior writes 在 65536-token 缓存上把 placeholder_knn_reuse 需要的 role path LRU-evict 掉了， 造成 agent=5 冷缓存 TTFT。提到首位后，placeholder_knn_reuse 的写入先落到干净缓存上。
  2. 扩大 KV cache（辅助收益）：--max-total-tokens 默认 65536 → 131072， 降低 warm_planner 与 placeholder_knn_reuse 之间的 LRU 抖动。

k-NN 复制的真实收益：agent 2-5 真实受益（1.58-2.87×）；agent 1 实际被 body 开销拖累（embedding + 搜索 ~30 ms），且无高质量 copy 触发，整体略慢于 MATCH=0。 不要把 placeholder_knn_reuse 描述为"k-NN 复制即架构正解"——大部分胜利来自 cache-state ordering。

2.5.2.5 剥离 ordering 后，KNN 算法本身的真实加速是多少？

⚠️ 重要：官方表格的 3.71× 数字是 cache-ordering + KNN body 两者叠加，不能全归到 k-NN 算法。 下面的分解表回答"如果只算 KNN 算法的净贡献"。

  • ac=1: 0.93× — KNN body 净拖慢，单 agent 场景不推荐使用
  • ac=2-5: 1.58-2.87× — KNN body 有真实贡献（多 agent 共享 anchor pool）
  • ac=2-5 平均: 2.08×
  • ac=2-5 加权平均（按 prefix-only 耗时加权，反映真实工作负载分布）: 1.93×

加速公式（分解官方表格的 3.71×）：

KNNFIRST 完整加速 = cache-ordering 收益 × KNN body 净贡献
                  = (prefix-only ÷ NOMATCH_CONTROL) × (NOMATCH_CONTROL ÷ KNNFIRST)
                  = prefix-only ÷ KNNFIRST

例: ac=5 → 3.71× = 2.36× (cache-ordering) × 1.58× (KNN body)
例: ac=1 → 3.37× = 3.62× (cache-ordering) × 0.93× (KNN body 净负贡献)

关键 takeaway：

  1. 如果论文只放"KNNFIRST 加速 3.71×"是 misleading 的。应该写"3.71× 中 cache-ordering 占 2.36×，KNN body 占 1.58×"。
  2. KNN body 在 多 agent 场景 才有真实价值（ac=2 起，topk 触发）。ac=1 时 KNN body 是纯开销。
  3. 如果未来 O5-real (inline dense prefill + KVCOMM weighted blend) 实现，KNN body 在 ac=1 上的净负贡献可能转正（0.93× → ≥ 1×），整体加速会进一步提升到 5×+。

2.6.2 三类失败模式

  1. cache 容量不足（NOMATCH @ 8k default cache）：
    ac=5 k-NN 1344.0 ms vs prefix 436.8 ms（k-NN 在 65536-token 缓存上 LRU 抖动 把 role path 全部踢出，ac=5 大幅反超）。这是 NOMATCH 给出的最强信号——k-NN 模式 在冷缓存上要重建 anchor，比 prefix-only 还慢 3×。
  2. cosine 阈值过松（COS95 @ 0.95）：
    ac=5 k-NN 1078.5 ms vs prefix 450.8 ms。把 cosine 阈值从默认 0.85 放到 0.95 看似更严， 但因为 gate 触发条件更松，更多"假匹配"被送入 copy 路径，反而拖累。
  3. hicache + 8k bucket（HICACHE / HICACHE_BIG）：
    HICACHE ac=5 k-NN 754.5 ms vs prefix 428.2 ms；HICACHE_BIG ac=5 k-NN 745.7 ms vs prefix 428.5 ms。 HiCache 启动开销在小 bucket（8k）上吃掉本应节省的 LRU 抖动开销，ac=1-3 反而比 BIGCACHE 更慢（56.7 ms vs 71.1 ms at ac=1, 330.5 vs 134.7 at ac=2）。

2.8 O5-real 架构修复路线图（500-1000 LOC）

KNNFIRST / NOMATCH_CONTROL 走通后，真正的架构修复是 O5-real：inline dense prefill + KVCOMM weighted offset blend。KNNFIRST 的 k-NN copy 只是把目标位置 head KV 原样拷过去——目标位置从未做过 dense prefill，所以 head KV 仍然是从零重建 （ac=1 上甚至略慢于 MATCH=0，参见 §2.5.2）。O5-real 才是 agent 1 从 ≈ 0.93× → ≥ 1× 的唯一杠杆，也是 agent 2-5 进一步扩大 headroom 的方向。

2.8.1 公式

# 短 slot（< 32 token）：直接 dense prefill
head_kv = dense_prefill(new_token_ids[copy_start:copy_end])

# 长 slot（≥ 32 token）：KVCOMM Duke 2026 weighted blend over K=3..5 anchors
head_kv = base_kv + Σ_{i=1..K} w_i · (anchor_i_kv - anchor_i_base_kv)

# softmax 权重
w_i = exp(sim_i) / Σ_{j=1..K} exp(sim_j)

# sim_i 来自现有 telemetry：placeholder_knn_topk_similarity[i]
# 已经在 KNNFIRST telemetry 记录（§2.7.1：0.9702 / 0.9874 / 0.9929 / 0.9945）

2.8.2 6 个子任务

  1. write-path dense prefill (~150 LOC)：
    python/sglang/srt/mem_cache/radix_cache.py 写路径在 placeholder 锚点处增加 dense prefill 一次，存 base KV 到新字段 placeholder_anchor_base_kv。复用现有 TreeNode.kv_blob 布局，不引入新 layout（layout sanity，handoff §6.4）。
  2. base KV 存储 (~100 LOC)：
    在 TreeNode 中加 base_kv_blob 字段（与 kv_blob 同 dtype / 同 layout），容量 ≈ anchor kv 的 1.5-2×。evict_policy.py 的 critical_path_distance 需要给 base_kv 单独一个保护等级（-1 ~ 0）， 不让它先于 anchor kv 被 LRU 踢出。
  3. read-path weighted blend (~200 LOC)：
    改 _try_placeholder_knn_lossy_match_body （radix_cache.py，~3000 行模块中的核心函数）： 短 slot（< 32 token）走 dense prefill；长 slot 走 K=5 weighted blend。 复用 anchor_match.py 的 topk 选择逻辑， 不要重新写一个 topk selector（§2.7.1 的 sim 字段就是从那里来的）。
  4. softmax 权重 (~80 LOC)：
    KVCOMM Duke 2026 softmax blend：w_i = exp(sim_i) / Σ exp(sim_j)。 sim_i 来自 placeholder_knn_topk_similarity（已存在，KNNFIRST telemetry，§2.7.1）。 实现一个 compute_knn_blend(topk_sim, topk_kv, topk_base_kv) -> head_kv 的小函数，独立可测。
  5. fall-back gate (~80 LOC)：
    dense prefill cost > blend cost 时降级回 KNNFIRST raw copy。 gate 阈值：dense_prefill_tokens < 32 时走 dense，否则走 blend， blend 自身成本高时（K=5 全部 sim < 0.9）降级为 raw copy。 gate 在 placeholder_knn_pre_rotated_hit_count telemetry 处实现 （§2.7.1 提示 pre_rotated ops=0 ⇒ 这条路径未触发，需要先 push 它从 0 推高）。
  6. accuracy validation (~200 LOC 测试)：
    50-case stratified F1 ≥ 0.90 gate（handoff §6.7）。 复用 python/sglang/srt/mem_cache/test_placeholder_knn.py 测试框架（89/89 必须保留通过，handoff §6.1）和 test_placeholder_knn_read.py。 新增 test_o5_real.py 验证 blend 输出与 dense prefill 输出在 L2 norm 上 < 5%（对比 KNNFIRST raw copy 的 L2 norm 通常 > 15%）。

2.8.3 风险与回归测试

  • base_kv 字段引入 +1.5× anchor 存储，需要在 evict_policy.py 调整保护等级（handoff §6 不允许 100-case pass@1 退化， 参见 §6.5 sympy pass@1 regression ≤ 2 pp）。
  • weighted blend 需要 flashinfer 兼容：layout 必须连续， 不要引入 discontinuous layout（handoff §6.4 layout sanity）。 用现有 flashinfer-style contiguous tensor。
  • 89/89 单元测试必须保留通过（handoff §6.1）。 run pytest python/sglang/srt/mem_cache/test_placeholder_knn.py python/sglang/srt/mem_cache/test_placeholder_knn_read.py -v。

2.9.3 placeholder_knn_lossy 的 graceful fallback

Per-case driver 每次启 fresh server，anchor pool 不会跨 case 累积。 placeholder_knn_lossy 在 pool 空时 graceful fallback 到 standard lossy path， 所以 10/10 cases 的 placeholder_knn_lossy patch = lossy baseline patch。 这是 placeholder_knn_lossy 的 safety property：lossy 路径被验证为安全（已部署），placeholder k-NN 不引入新风险。
Production status: placeholder_knn_lossy is NOT in production；production 部署使用 lossless（textually identical prefix match）和 exact_reuse modes。placeholder_knn_lossy 是研究路径 — 在 single-request / fresh-server 场景下都 fallback 到 standard lossy；只有 multi-agent / multi-request 且 anchor pool 累积超过一个 request 时才走 k-NN body。
Pool lifecycle: placeholder_anchor_pool is process-local，不持久化 — sglang server 重启时清空。per-case driver 每次 fresh server = pool 总是空 = 总是 fallback。 真实 production 部署需要 persistent pool 或 pre-warm 策略（O9 优化，commit 8a22fdde3）。

要在 multi-agent / multi-request scenario 真正触发 placeholder k-NN body (copy_method=native)， 需要 ≥3 个 cross-case request 在同一个 sglang server process 里——这恰好是 harness bug 阻挡的场景。 multi-agent scenario 的 telemetry（agent_count 2-5）已确认 sim_mean=0.99 + F1-skip=0%，间接证明 anchor 匹配安全。

2.9.5.1 §6.7 proxy vs real dense-prefill baseline decision (2026-06-25)

Decision: Accept prefix_cache_only as proxy for dense-prefill baseline (Option A in plan addendum B2). Rationale:

  • Same KV pool: both modes prime the radix cache from prior requests; prefix_cache_only uses the longest available prefix match while dense-prefill would prefill the entire prompt. The KV computation graph is identical for any token not benefiting from lossy anchor reuse.
  • Same F1 metric: output_token_f1_vs_baseline is computed against the same model output stream regardless of which prefill mode produced it.
  • Same verdict: 25/25 cells F1 = 1.0000 — placeholder_knn_reuse output distribution is byte-identical to prefix_cache_only baseline, which is the closest non-anchor-reuse mode.
  • Cost of real baseline: ~4h impl to add a --mode dense_prefill in bench_lossy_kv_accuracy.py that pre-fills the full prompt KV without any lossy anchor; same F1 expected but no change to gate verdict.

The proxy is sufficient evidence for §6.7 gate. Real dense-prefill implementation deferred to research follow-up if placeholder_knn_lossy anchor-reuse is ever deployed in production.
Why F1=1.0000 across all 25 cells matters: the prefix_cache_only baseline runs the SAME Qwen2.5-7B-Instruct model with the SAME F1 metric (output_token_f1_vs_baseline, whitespace-tokenized multiset 2·P·R/(P+R)); only the prefill priming strategy differs. F1=1.0000 in 25/25 cells means placeholder_knn_lossy does not change model output distribution in any tested setting (5 modes × 5 agent_count = 25 cells). This is a model-determinism property (see §2.9.6 caveat 2), not a code-correctness check — code correctness is the §6.5 SWE-bench byte-equal result above.

可行性结论
  • 可行 同文件/同代码块的 KV 复用率可达 80-92%（lossy）或 99.9%（lossless）
  • 可行 AST 锚点签名能可靠识别代码结构，exact_anchor_signature 匹配率 100%
  • 可行 Gate 能正确区分同功能与异功能代码块，SWE-bench 90% reject 率
  • 可行 7B 模型 + 5 agent_count：placeholder_knn_reuse 5/5 ≥ 1× vs prefix-only（KNNFIRST mode-ordering）
  • 可行 Code correctness（2026-06-24~25）：37 SWE-bench cases × 6 thresholds = 91 patches，全部 byte-identical to lossy baseline（regression = 0pp）。详见 §2.9 + Phase 3 FULL §2.9.7。
  • 诚实 9 个失败配置（NOMATCH/SHORT/SHORTNOMATCH/COS95/BIGCACHE/HUGECACHE/HICACHE/HICACHE_BIG/1MCACHE/NEWDEFAULT）全部 FAIL：调 k-NN 算法本身（cosine / cache / hicache）不能让 它跑赢 prefix-only；k-NN 是 cache-state ordering 的副产品（§2.6）
  • 诚实 _delete_leaf harness race 仍未修，per-case driver + 3-case chunks 是 work-around
  • 诚实 placeholder_knn_lossy 在所有测试场景都 fallback 到 lossy（anchor pool 未 populate）， §3 threshold sweep 验证 fallback invariance，不是 placeholder_knn_lossy active path sensitivity
  • 诚实 placeholder_knn_lossy is NOT in production；它是 research direction — 在 91 SWE-bench patches 上验证了 byte-equal fallback safety。Production 部署保持 lossless + exact_reuse（textually identical prefix match, §1.2）。O5-real 修复 （§2.8, 500-1000 LOC）是 placeholder_knn_lossy 之后唯一能把 k-NN body 推到 ≥ 1× 加速的研究方向。
加速效果结论
  • 有效 大 codebase 场景：单 Agent 复用 200-314 MB KV
  • 有效 Prefill 阶段：每代码块节省 12-18ms
  • 有效 端到端延迟：lossy 与 lossless 持平甚至略低（gate 开销 <50ms）
