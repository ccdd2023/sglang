核心问题与三次尝试

"code structure 能决定 KV cache 重算什么吗？" — 若能，则可在等预算下买到精度，使 lossy reuse 成为 accuracy-preserving speedup。

为什么 Direction A 是 −3.3pp？

HKVD 直接回答了 Direction A 的失败机制 — 不是"机制不够好"，而是"方向反了"。

token 组K_dev对 prefix swap 敏感？Direction A 策略结果
interface (sig+docstring)0.0843较低（声明性、自包含）recompute（重算稳定的）浪费预算
body (逻辑、self.attr、calls)0.0886较高（依赖 context）copy（保留 stale 的）精度损失

最坏 selective 策略：重算了本来就稳定的 interface KV，保留了敏感 body 的 stale KV。R32 uniform 至少随机覆盖前缀，有概率命中敏感 body tokens → R32 9.8% > nodekind 6.6%。

V_dev 反方向（interface 0.0100 > body 0.0061）但 V_dev 整体小 6×，attention 匹配由 K 主导；且 K/V 不能分开 recompute。不足以支撑 selective 策略。

局限：HKVD 测的是 prefill KV deviation（canonical→live prefix swap），未测生成时 attention 动态；n=15 + OOM drops 使 CI 宽；verdict 精度 ≠ 任务能力。

附录 · 限制与边界

本研究的边界

  • 单一模型：仅 Qwen2.5-Coder-7B。更大模型 / 不同 family 的 HKVD pattern 未验证 — interface/body deviation 差异可能模型相关。
  • 单一 benchmark：pandas_15case_v1（verdict task）。code-gen / 其他 repo 未覆盖。
  • HKVD 测量边界：canonical→live prefix swap 是 pool precompute 的真实场景，但只测 prefill KV；decode 阶段的 attention 动态未测。
  • n=15 + deterministic OOM：task 7 OOM 使 R32_f045 只有 61/75 rows；CI 宽。paired test 缓解但未消除。
  • contiguous head 是测过的唯一 selective 机制：per-token mask (CacheBlend) 未实现，"机制错 vs 信号错"的区分依赖 HKVD 推断而非直接 per-token 实验。
  • verdict 精度 ≠ 任务能力：R38b verdict 5/25 = lossless 但 code-gen git apply 0/5 vs 1/5（slide 28 R40-P2）。

三重证伪在当前 setup 下成立；外推到其他模型/task 需重新验证 HKVD-by-node-kind。
