Debug story

为什么旧 Phase 2 结论不能用

旧结果看起来像 extended 比 oracle 慢很多，但根因是 benchmark 设计污染了对比，不是 server 里存在 mode-specific 慢路径。

1. Shared-cache contamination

旧 driver 按固定顺序跑 modes，oracle 紧跟 extended，可能复用了 extended 刚插入的 KV。这个顺序让 oracle 获得了不公平的 warm state。

2. Measurement fixes

新 benchmark 默认每个 mode 先 flush cache，再只 warmup 自己的 mode，然后测目标请求。同时修复 streaming output F1 读取。

3. Safety guard

新增 --context-aware-max-predicted-d 2.0，用 predicted KV distance 拒绝高风险 exact-content matches，保住 F1。

Takeaway for teachers

本周的重点：从“能复用”走向“可证明地安全复用”

Compared with last week's simple AST locator, this week's code-specific reuse adds broader code spans, exact-content verification, predicted-distance risk control, isolated benchmark methodology, and richer diagnostics.

简单说：AST 负责找到哪里可能复用，内容签名和 predicted-d guard 决定能不能复用；benchmark 则确保我们测到的是方法本身，而不是 cache 顺序污染。
