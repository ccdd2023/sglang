(1) 目标 & 硬约束（回顾）

用户原始问题

「利用 coding 任务的结构化特征，在保证复用更多 KV cache 的前提下，选择性地复用损失小的 KV。每次算法迭代都要用实验验证 accuracy 和 speedup。」

5 条5 条硬约束（不可违反）

  • accuracy 必须可量化 — verdict 通过/失败/未识别 + 故障类型与 lossless 的一致率
  • prompt 必须字节级一致 — 不修改 prompt 顺序或内容；只允许 reuse 决策变化
  • 加速必须来自更多复用 — 不允许 KV-cache 调度的小聪明
  • 新特性默认 OFF — 通过环境变量显式开启
  • 可用 deep research — 寻找算法候选

本周交付的核心 Pareto

按块位置分层的 FRAC (R38b) = (FRAC_EARLY=0.60, FRAC_LATE=0.15, EARLY_N=2) — 7B-Coder × 5 verdict task; +8.3pp type_agreement, -0.9% TTFT, +38% code-aware 复用; 3× 字节级精确复现。详细 benchmark 配置见下页。

(4) 术语解释 — 后面所有 slide 都会用到

类别 / 名词含义
lossless无复用 — 每个请求从 token 1 重新算 KV。黄金 baseline，但最慢
radix prefix cache前缀 KV 树（字节级精确）— 匹配前缀直接复用（前约 110 token）
AST-chunk pool按函数/class 切块的预计算 codebase KV — 本 deck 主要讨论这一层
copy_pool从 chunk pool 直接 copy KV（含 RoPE 位置校正）— 命中后的默认动作
head_recomputechunk 头 K 个 token 自己 dense_prefill，body 仍然 copy — FRAC 杠杆所在
dense_prefill整段重新算（不 copy）— 池里没命中，或被 selective refresh 跳过
HKVD（High KV Deviation）CacheBlend 的核心信号：copy vs fresh prefill 下两组 K/V 的逐元素偏差。本 deck 用位置代理代替 HKVD（见 slide ⑭）
canonical prefix / prompt_align预计算时用的标准 preamble + 运行时对齐到 live prompt → 让 prefix 进 radix。CANONICAL_PREFIX=1 + PROMPT_ALIGN=1
multi-slot / CacheBlend staging5 个 chunk 在 GPU 上紧挨着连续排放（slot 间无 header），一个 prefill 完成所有 copy + 重算
gap-prefill相邻 chunk 间 byte 不连续的段落 → 必须 dense_prefill（不能 copy）

2 个核心评估指标 + FRAC 杠杆

TTFT (ms) — 复用者从请求到首 token 的延迟。↓ 越低越好（speed）。
type_agreement (%) — 输出故障类型与 lossless 一致的比例。↑ 越高越好，primary accuracy 指标。
FRAC = 0.30（例）→ 每个被选中的 chunk，前 30% token 自己 dense_prefill，剩下 70% 直接 copy。
FRAC_EARLY / FRAC_LATE：前 EARLY_N=2 个 chunk 走 EARLY 档（0.60），第 3 个起走 LATE 档（0.15）。 直觉：早期 chunk 离跨上下文前缀边界最近 → stale KV 风险最高 → 多算一点；后期多 copy。

Pareto front

Pareto front = (speed, accuracy) 双目标下没有其他 config 同时更快、更准的配置集合。标题 slide 的曲线 = R19 → R32 → R37 → R38b 的 Pareto front（越高越准、越左越快 = 越好）。

结论

Phase 2 K 余弦分离度 = 0.040 ≈ 4% 的 K 信息与上下文相关。剩下 96% 是结构而非内容，但这 4% 正好处于跨上下文边界，是 live query 中 attention 的聚焦位置，所以产生了丢失精度的效果。 推论：字节级精确的非前缀复用本质上就是有损的；选择性重算（R32/R38b）是原则上的缓解方案。

(9) 预计算 流水线 — 离线代码库 KV → host 池 → 运行时 GPU 拷贝

Stage 1 — 离线预计算（scripts/precompute_codebase_kv_v4.py）

驱动一个进程内的 ModelRunner，通过 ASTChunker 切块，从 kv_pool.k_buffer[layer][out_cache_loc] 抽取每层 K/V，每个 chunk 序列化为一个 .bin 文件加 manifest.jsonl。输出目录: 结果s/codebase_kv/pandas_5case_v4/{chunks/,manifest.jsonl,preamble.txt,preamble_token_ids.json,meta.json}（约 880 MB，5 case × 5 segment × 28 层 × bfloat16）。

Stage 2 — 服务启动时的加载器（codebase_kv_loader.py）

加载到一个独立的第二个 MHATokenToKVPoolHost（codebase_host_pool，bump-allocator，永远不会被 LRU 驱逐），校验 meta.json（head_num、head_dim、layer_num、dtype、layout），对存储的 token_ids 重新分词以检测 preamble 漂移，用 ChunkKVEntry 填充 RadixCache.placeholder_chunk_pool，其中 kv_indices 指向 host 槽位。

Stage 3 — 读路径（radix_cache.py 中的 _build_chunk_plan）

对每个请求做字节级精确的 chunk 查询 → CPU→GPU 传输（move_kv_cache）→ 就像这个 chunk 是现场算出来的一样复用。两个 host 池（radix-eviction 与 codebase-dedicated）是正确性的关键杠杆。

(12) CacheBlend deep research（R31）— 99 个 sub-agent 扇出调查，HKVD 选优

调研范围

5 个角度：CacheBlend、SnapKV、StreamingLLM、RazorAttention、2025-2026 年代的 code-aware 后续工作。99 个 sub-agent，300 万 tokens，17 个确认 / 8 个被否定。

核心发现

CacheBlend (arXiv:2405.16444) 是唯一被实证能恢复跨上下文精度的算法。

  • 每层 5–18% 的 HKVD（高 KV 偏差）token，默认 15%
  • Layer-by-layer gradual filter: r1 > r2 > ... > r*
  • 代价: 重算 3ms/层 vs 从 NVMe 加载 16ms/层 → 重算比加载更快
  • 相比全量重算最多差 0.002 F1/Rouge-L（多文档 QA）
  • 相比全量重算 TTFT 加速 2.2–3.3×

局限：没有 code-generation 或 SWE-bench 评测。Code-aware 复用的 dynamics 不同，需要适配。

5 方案的核心差异 — 一图看清

FRAC 决定了「copy 多少 vs 重算多少」。
lossless：FRAC = 100%（全算，无 copy）。L2/L4：FRAC = 0%（全 copy，无重算）→ stale KV 风险最大。
R32：FRAC = 30%（常数）→ 所有 chunk 同等对待。R38b：FRAC = {60%, 15%}（按位置分两档）。
R38b 的关键洞察：早期 chunk 离跨上下文前缀边界最近，stale KV 影响最大 → FRAC 应该更高；后期 chunk 已经在 cache prefix 之内 → FRAC 可以更低。

(18) 为什么 (FRAC_EARLY=0.60, FRAC_LATE=0.15, N=2) 能赢

位置特异性的风险聚集

请求序列中的早期 chunk离跨上下文前缀边界最近（system message + role + case + instruction）。那里的 attention 最受 live query preamble 的干扰。

请求序列中的后期 chunk已经建立了 cache prefix，attention 分布在跨 prefix 时更稳定，可以更激进地 copy。

R38b 近似 CacheBlend 的 per-layer r1 > r2 > r* 过滤

CacheBlend §4.3:
  layer 1:    r1 > r* tokens → recompute
  layer 2:    r2 < r1 tokens → recompute（逐层渐缩）
  ...
  layer L:    r* tokens → recompute（默认 15%）

R38b 的简化版（per-chunk-position，不是 per-layer）:
  chunk 1-2:  FRAC = 0.60  ← 高（跨上下文边界）
  chunk 3+:   FRAC = 0.15  ← 低（cache prefix 已建立）

关键优势：不用修改 attention-kernel，只在 _build_chunk_plan 内部的 reuse 决策上做文章。Prompt 完全不动。

附录 B — imports-prelude 预置 (R33) · 违反 prompt 约束 → 撤回

假设

在 user body 顶部 prepend 顶层 import 段（如 import numpy as np; import pandas as pd），让 library API surface 在跨上下文时保持一致，减少因 import 缺失导致的幻觉。

实现

附录 C — 类型注解门控 (R34) · pandas 0.x 无类型注解 → 退役

假设

query chunk 含有类型注解（def foo(x: int) -> str:）时 → 上调该 chunk 的 FRAC 到 0.50（vs 默认 0.30）。理由：类型注解让函数签名更精确，跨上下文复制时头部 token 更容易「代入错误实参语义」，需要更多重算。

实现

helper = ast_chunker._extract_type_signature_string  # 抽取 chunk 的类型签名
if helper(chunk) and len(helper(chunk)) > 0:
    plan.frac_override = 0.50  # 上调 FRAC
else:
    plan.frac_override = None   # 用全局默认

实测（7B-Coder × 5 verdict task on pandas 0.x）

故障类型一致率 41.7% → 33.3%（退化 8.4pp）

根因：pandas 0.x 代码库几乎没有类型注解（0.x 时代 Python 还未普及 typing）。helper 对绝大多数 chunk 返回 "" → 门控退化为「全局 FRAC 提升到 0.50」，超过 R32 的 0.30 Pareto 点。

未来重测路径

  • 在有类型注解的代码库上重测：SWE-bench 的 django、astropy、sphinx 等 2.x+ 项目预计有 30-80% 函数带类型注解，门控会真正生效。
  • 需要重新生成预计算池：scripts/precompute_codebase_kv_v4.py 的 AST-chunker 已经支持类型注解抽取（保留为 helper），只需新代码库的 .py 集合。

根因
