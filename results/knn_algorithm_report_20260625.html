2. Placeholder k-NN 算法 — 5 步执行流程

2.1 触发条件（3 个必须全部满足）

  1. SGLANG_PLACEHOLDER_KNN_MATCH=1（默认 0 = 关闭）
  2. req.placeholder_anchor_token_spans 非空（AST 锚点 spans）
  3. Embedder 已加载（semantic_suffix.is_enabled() and load_embedder() != None）

任一条件不满足 → 直接 return，走 lossy 路径 fallback（这就是 §2.9 byte-equal 结果的来源）。

调用栈（radix_cache.py:680-691）：

match_prefix(req, key)
  ├── _try_lossy_fuzzy_match(req, key, value, last_node)    # 路径 1: textually-identical
  ├── _try_placeholder_knn_lossy_match(req, key, ...)       # 路径 2: placeholder k-NN  ← 本文
  └── (如果 value 非空) torch.cat(value)

2.2 5 步算法详解

1Placeholder 锚点建立（write path）

在 radix cache 写入路径上，对每个 AST 锚点：

with self.anchor_kv_store_lock:
    self.anchor_kv_store.setdefault(
        segment_content_signature, []  # 按 code content SHA-1 索引
    ).append(entry)                    # entry: AnchorKVEntry(KV blob + 签名)

# 另一个独立池: placeholder_anchor_pool (radix_cache.py:555)
# 索引 key: slot_id (AST 锚点角色位置)
# value: list of AnchorKVEntry with pool_embedding 已计算

关键区别：anchor_kv_store 按"代码内容"索引（textual identical 复用）； placeholder_anchor_pool 按"AST 锚点角色"索引（cosine similar 复用）。

2读路径触发（read path）

placeholder_anchor_token_spans 由 anchor_match.py:build_anchor_metadata 在请求到达时 根据 prompt 中的 AST 锚点提取，每个 span = (slot_id, start_token, end_token)。

spans = getattr(req, "placeholder_anchor_token_spans", None) or []
if not spans:
    return exact_values, exact_node
3k-NN 搜索（核心）

对每个 span：算 embedding → top-K cosine 搜索 → 过滤 sim < 阈值

top_k = int(os.environ.get("SGLANG_PLACEHOLDER_KNN_TOPK", "4"))
min_cos = float(os.environ.get("SGLANG_PLACEHOLDER_KNN_MIN_COSINE", "0.70"))

# _placeholder_knn_search (radix_cache.py:128-170)
sims = (embeddings @ q.T).squeeze(1)   # cosine 相似度
top_sims, top_idx = torch.topk(sims, k=K)
for sim, idx in ...:
    if sim < min_cos: break
    out.append((valid[idx], float(sim)))

O1-O9 优化跳过（默认关闭，env-var 控制）：

  • O7: MIN_NEW_TOKENS > new_token_count 跳过（默认 0）
  • O8: MAX_SPAN_OVERLAP_RATIO < prefix_already_covered 跳过（默认 1.0）
  • O2: MAX_ROPE_OPS < entry_len × layer_num 跳过（默认 114688 开启）
  • O1: MAX_OVERLAP_RATIO < overlap_ratio 跳过（默认 0.5 开启）
4KV 复制

把 K 个 anchor 的 KV 原样复制到当前 prefill stream 的目标位置。

for sim, entry in top_k_results:
    if sim >= min_cos:
        copied_kv = entry.kv_blob.to(device)
        # O5-lite: 只对前 head_tokens 个 token 做 RoPE 旋转
        if SGLANG_PLACEHOLDER_KNN_PRE_ROTATE_DELTAS:
            copied_kv[:head_tokens] = apply_rope_delta(...)
        exact_values[start:end] = copied_kv

重要：这是原样复制——没有 dense prefill，没有 weighted blend。 由于 head_rot_total_ops = 0（§2.7.1 telemetry），O5-lite 实际从未触发， 真正在跑的 KNNFIRST 是 raw copy。

5继续生成（decode）

复制好的 KV 替换了原本要从零计算的 prefix KV。模型把"近似 KV"当作真实 KV 使用，开始 decode。

关键假设：

  • sim ≥ 0.97 时，anchor 的 KV 与目标位置的真实 dense-prefilled KV 数值差异 < 5%（L2 norm）
  • 模型对 KV 的小幅差异鲁棒（不累积误差）
  • 输出分布不变（§6.7 F1=1.0000 在 25/25 cells 验证）

3. 与 Code-Aware 复用的整合

3.2 关键集成点 1: AST 锚点作为 placeholder 边界

AST 锚点（函数定义、类定义、装饰器、import 等结构边界）是 placeholder k-NN 的对齐边界。具体流程：

  1. 请求预处理（anchor_match.py:build_anchor_metadata）： placeholder_anchor_token_spans = extract_anchors_from_prompt(code_anchor_spans, prompt_token_ids)
  2. AST 锚点只决定"在哪里切"，不改变代码内容：
    • 不会"用相似代码替换原代码"
    • 只是给 k-NN 提供"在哪些位置可以做替换"的提示

这是为什么 code_aware_kv_reuse_exact_text_match memory 说： "AST 锚点只决定对齐边界，不接受结构相似但文本不同的代码"。

3.3 关键集成点 2: lossy_alignment_method = 'kvcomm'

在请求元数据中，k-NN body 显式选择 alignment method：

"lossy_alignment_method": "kvcomm"   # bench_coding_kvflow_prefetch.py:290

kvcomm 是 KVCOMM Duke 2026 的 alignment：把 anchor 的 KV 整体平移到目标位置（不做旋转 blend）。 O5-real 才会升级为 weighted blend（见 §5）。

3.4 关键集成点 3: F1 skip-rate gate（§6.8）

placeholder_knn_lossy 的"安全契约"靠 F1=1.0 间接保证：

anchor 触发 → 复制 KV → 生成 token → 算 F1 (vs no-cache baseline)
                                            ↓
                                  F1 ≥ 0.9: 接受
                                  F1 < 0.9: 计入 skip_LF1, anchor 标 bad

placeholder_anchor_store_skipped_low_f1_count 是 §6.8 gate 的指标。实测 25/25 cells skip rate = 0%（§6.8 PASS）。

3.5 与 lossy 路径的对比

维度lossy (Path 1)placeholder_knn_lossy (Path 2)
触发条件AST 锚点文本 byte-identicalAST 锚点 cosine ≥ 0.85
数据源anchor_kv_storeplaceholder_anchor_pool

关键：两条路径在同一 match_prefix 串行执行， placeholder_knn_lossy 在 lossy 失败（无 exact match）时补一刀，理论上能再多省 5-15% prefill。

4.2 为什么 9 个调 cache 容量/cosine/hicache 的配置都失败

共同的失败模式：ac=5 都在 745-1344 ms 区间，prefix-only 被压在 427-476 ms 区间。 k-NN 模式在 ac=5 上比 prefix-only 慢 1.5-3× 持续存在。

具体看 NOMATCH 配置（最直白）：

  • ac=5 k-NN 1344.0 ms vs prefix 436.8 ms
  • k-NN 在 65536-token 缓存上 LRU 抖动把 role path 全部踢出，ac=5 大幅反超
  • 这是最强的信号：cache 容量本身不是瓶颈，cache 状态是

根因：radix cache 是 LRU 淘汰制，容量上限 65536 token。 在 5 个 agent 跑 4 个 prior mode 之后：

agent 1: 4 mode prior writes  → 占满 cache
agent 2: 4 mode prior writes  → 把 agent 1 的 KV LRU 踢出
agent 3: 4 mode prior writes  → 把 agent 1, 2 的 KV LRU 踢出
agent 4: 4 mode prior writes  → 把 agent 1, 2, 3 的 KV LRU 踢出
agent 5: 4 mode prior writes  → cache 里只剩 agent 5 自己的最后 1 个 mode
        placeholder_knn_reuse 想读 role path？已经被踢出 → 重新计算 prefix KV

3 个失败旋钮的共同点：它们都在调怎么算 k-NN（cache size、cosine、hicache）， 但不解决"在 65536-token cache 里，placeholder_knn_reuse 写入时 role path 已被踢出"的问题。

4.3 突破 1: REVERSE mode-order（假突破）

REVERSE 把 --agent-counts 从 1,2,3,4,5 改成 5,4,3,2,1。 ac=5 单独走通 2.94×：

acNEWDEFAULT pk / preREVERSE pk / pre现象

2152.9 / 286.3139.9 / 78.4同上

REVERSE 证明：失败主要是 cache state ordering，不是 k-NN 本身。 但 REVERSE 不是合法解决方案——它只是把"先到先得"反转，让最后跑的 ac=1 吃到 ac=5 大请求留下的 cache 残留。 ac=4 因此反而退化到 776 ms。

4.4 突破 2: KNNFIRST mode-ordering（真突破）

KNNFIRST 把 placeholder_knn_reuse 移到 CORE_TTFT_MODES 第一位 （紧跟 warm_planner 之后），并把 --max-total-tokens 从 65536 提到 131072：

CORE_TTFT_MODES = [warm_planner, placeholder_knn_reuse, agenttemplatekv_*, ...]
                                          ↑ 第一个跑的 mode

机制：

  1. placeholder_knn_reuse 是第一个跑（紧跟 warm_planner），写入的 KV 落到干净 cache上
  2. 后面 4 个 mode 的 prior writes 反而会被它的 KV 顶到 LRU 末端（如果它们用不到） → cache 里剩下的就是 placeholder_knn_reuse 路径真正需要的 role path
  3. 131072-token cache 提供足够容量，让 5 agents × 4 modes = 20 个 prior writes 不会把 placeholder_knn_reuse 的 KV 踢出

4.5 NOMATCH_CONTROL 证明 k-NN body 几乎无贡献

NOMATCH_CONTROL = KNNFIRST 的 mode 顺序 + cache 容量 + MATCH=0（关掉 k-NN body）：

agent_count NOMATCH_CONTROL (ms) KNNFIRST (ms) cache-ordering 收益 k-NN 复制净收益
169.374.33.66×≈ 0.93×（无明显收益）
2350.2121.91.43×≈ 2.87×
3410.0197.71.85×≈ 2.07×
4469.3262.72.15×≈ 1.79×
5536.5340.42.36×≈ 1.58×

列解读：

  • cache-ordering 收益 = prefix-only ÷ NOMATCH_CONTROL （即"把 mode 移到第一位 + 131072 cache"带来的加速，与 k-NN 无关）
  • k-NN 复制净收益 = NOMATCH_CONTROL ÷ KNNFIRST （即 k-NN body 本身带来的额外加速，< 1× 表示 body 净拖慢）
结论：
  • ac=1 的 3.37× 加速 100% 来自 cache-ordering（NOMATCH_CONTROL 已经能拿 3.66×）， k-NN body 反而拖慢 7%
  • ac=2-5 cache-ordering 仍然占主导（1.43-2.36×），k-NN body 额外贡献 1.58-2.87×
  • 整体 3.71× 是两者叠加，但 cache-ordering 是更基础的杠杆—— 不调 mode 顺序，单纯调 k-NN 算法本身（cosine / cache / hicache）不能让 ac=5 跑赢 prefix-only

5. Placeholder k-NN 与 Code-Aware 复用的真正边界

5.1 安全契约的差异

路径触发条件安全保证失败处理
lossless (生产)byte-identical prefix输入字节完全一致 → 数学上 100% 安全无匹配 → dense prefill
exact_reuse (生产)AST 锚点 + textually identical segment文本完全一致 → 100% 安全无匹配 → dense prefill
lossy (生产)AST 锚点 + exact_anchor_signature match文本完全一致（按 anchor signature 算）无匹配 → dense prefill
placeholder_knn_lossy (研究) AST 锚点 + cosine sim ≥ 0.85 间接：F1=1.0 输出分布不变 sim < 阈值 → fallback lossy

placeholder k-NN 路径不提供 byte-identical 保证——它靠"输出分布不变"来间接保证安全。 生产部署不用它，因为：

  • 任何 < 1.0 的 F1 都意味着某些 case 输出分布漂移
  • cos 0.85-0.95 区间 F1 仍 ≈ 1.0 但无法数学证明
  • 0.99 阈值下 F1 严格 = 1.0，但 cache hit rate 下降到与 lossy 几乎无异

5.2 与 code-aware 复用的关系

placeholder k-NN 是 lossy 路径的扩展，不是替代品：

  1. 复用条件放宽：textually identical → cosine similar（参数化 min_cos）
  2. 数据源扩展：anchor_kv_store（content-signature 索引）→ placeholder_anchor_pool（slot-id 索引）
  3. 写入时机不同：lossy 写入时无 embedding 计算；placeholder k-NN 写入时为每 slot 算 embedding （额外 ~24ms per slot）
  4. 运行时开销：lossy 几乎无开销（hash lookup）；placeholder k-NN 有 embedding 算 + topk search + RoPE 旋转，~5-30ms per slot

为什么不能完全替代 lossy：placeholder k-NN 的 cache hit rate < lossy （cosine 相似性比 byte-identical 更挑剔），所以在大多数生产 prompt 上，placeholder k-NN 触发次数 < lossy， 不是"更激进就更好"。

5.3 O5-real 路线图（未来方向）

KNNFIRST 的 k-NN body 只做原样复制——目标位置从未做过 dense prefill， 所以 head KV 仍然是从零重建（ac=1 上甚至略慢于 MATCH=0）。

O5-real = inline dense prefill + KVCOMM weighted offset blend： 
# 短 slot (< 32 token)：直接 dense prefill
head_kv = dense_prefill(new_token_ids[copy_start:copy_end])

# 长 slot (≥ 32 token)：KVCOMM weighted blend over K=3..5 anchors
head_kv = base_kv + Σ_{i=1..K} w_i · (anchor_i_kv - anchor_i_base_kv)

# softmax 权重
w_i = exp(sim_i) / Σ_{j=1..K} exp(sim_j)

预期效果：

  • ac=1 从 ≈ 0.93× → ≥ 1×（目前 KNNFIRST body 净拖慢）
  • ac=2-5 进一步扩大 headroom（目前 1.58-2.87× → 估计 2-3×）
  • 500-1000 LOC，~2-3 天实现，依赖 P2 C1 (_delete_leaf race fix)

6. 关键 takeaway

1. 算法 = 5 步

placeholder k-NN = AST 锚点 → embedding → top-K cosine → KV 复制 → decode。核心是"按 AST 锚点切，按 cosine 找相似，按 slot 复制 KV"。

2. 它是 lossy 的扩展

cosine ≥ 0.85 比 byte-identical 更宽，但 cache hit rate 更低，生产不用，研究用。

3. 加速 90% 来自 cache-ordering

把 placeholder_knn_reuse 放到 CORE_TTFT_MODES 第一位 + 131072-token cache 解决"在 65536 cache 里 KV 被 LRU 踢出"的问题。k-NN body 本身在 ac=1 上净拖慢（≈ 0.93×），只在 ac=2-5 真正贡献 1.58-2.87×。

4. 不调 mode 顺序 = 失败

单纯调 k-NN 算法（cosine/cache/hicache）不能让 ac=5 跑赢 prefix-only。这是 9 个失败配置的共同教训。

5. 生产路径不变

placeholder_knn_lossy 是 research direction，production 仍用 textually-identical prefix match (lossless / exact_reuse / lossy)。

6. 安全由 F1 间接保证

§6.7 F1=1.0000 (25/25 cells) + §6.5 SWE-bench 91/91 byte-equal 验证了 v44 的安全性，但生产部署保持更严格的"输入字节完全一致"契约。

6. 剥离 ordering 后，KNN 算法本身的真实加速是多少？

⚠️ 重要：官方表格的 3.71× 数字是 cache-ordering + KNN body 两者叠加，不能全归到 k-NN 算法。 下面的分解表回答"如果只算 KNN 算法的净贡献"。

6.1 实验设置

对比 KNNFIRST (MATCH=1) vs NOMATCH_CONTROL (MATCH=0)——同 cache (131072)、同 mode 顺序， 仅 KNN body 开/关。这是 KNN 算法净贡献的公平对比。

6.3 加速公式（分解官方表格的 3.71×）

KNNFIRST 完整加速 = cache-ordering 收益 × KNN body 净贡献
                  = (prefix-only ÷ NOMATCH_CONTROL) × (NOMATCH_CONTROL ÷ KNNFIRST)
                  = prefix-only ÷ KNNFIRST

例: ac=5 → 3.71× = 2.36× (cache-ordering) × 1.58× (KNN body)
例: ac=1 → 3.37× = 3.62× (cache-ordering) × 0.93× (KNN body 净负贡献)

6.5 关键 takeaway

  1. 如果论文只放"KNNFIRST 加速 3.71×"是 misleading 的。应该写"3.71× 中 cache-ordering 占 2.36×，KNN body 占 1.58×"。
  2. KNN body 在多 agent 场景才有真实价值（ac=2 起，topk 触发）。ac=1 时 KNN body 是纯开销。
  3. 未来 O5-real (inline dense prefill + KVCOMM weighted blend) 实现后，KNN body 在 ac=1 上的净负贡献可能转正（0.93× → ≥ 1×），整体加速会进一步提升到 5×+。

6.6 与"和 lossless 对比是否公平"的对应关系

这一节也回答了"KNNFIRST vs prefix-only 的对比是否公平"的问题。

不公平点：

  1. cache 容量不同（KNNFIRST 131072 vs prefix-only 65536）
  2. prefix-only 跑得少（5 次 vs 20+ 次 prior writes）

公平对比应当用 NOMATCH_CONTROL（剥离 KNN body），本节 §6.2-6.4 即为公平对比的结果。

7.2 三个维度的"赢家"

  • TTFT 加速：KNNFIRST 3.71× > AST 1.193× > Graph 0.87× (1 agent) KNN 路径是 TTFT 维度上对现有路径的补充
  • SWE-bench apply_ok 准确度：Graph 15/24 (62.5%) > Lossy 13/24 > Lossless 12/24 Graph 是 SWE-bench 准确度维度上对现有路径的补充
  • 输出分布稳定性：KNN F1=1.0000 (model determinism) > AST F1=0.9914 (有 0.86% 偏差) KNN 在 F1 维度上更稳定（前提是 model determinism 成立）

7.3 三者的真正关系（trade-off，不是替代）

TTFT 加速:    KNN (3.71×) > AST (1.193×) > Graph (0.87×) > Lossy (0.65×) > Lossless (1.00×)
SWE apply_ok: Graph (15/24) > Lossy (13/24) > Lossless (12/24) > AST (未测) > KNN (2/27, 与 lossy 一致)
F1 vs base:   KNN (1.0000) > AST (0.9914) > Graph (未测) > Lossy/Lossless (1.0 by definition)
覆盖率:       AST (28/28) > Graph (24/28) > KNN (5 agents, 不直接可比)

结论: KNN 适合加速 + 输出稳定的场景
     Graph 适合需要 SWE-bench 准确度的场景
     AST 适合追求覆盖率 + F1 均衡的场景

7.4 为什么 KNN 在 apply_ok 维度上不比 Lossy 强

KNNFIRST 的 §6.5 SWE-bench 验证是"v44 vs lossy baseline 的相对精度"（regression = 0pp）， 不是"KNN vs lossy 的绝对精度"。

  • KNN 走的是 cos ≥ 0.85 相似锚点复用
  • Lossy 走的是 exact anchor signature 复用
  • 在 SWE-bench 这种"代码功能必须 100% 对"的场景里，cos 0.85 复用反而有风险（虽然 F1=1.0 显示安全）
  • KNN 的设计目标是加速而不是提升准确度，所以两者的"代码准确度"应当持平（KNN 不退化也不提升）
  • KNN = lossy in 准确度，KNN > lossy in TTFT（多 agent 场景）

7.5 未来方向

  • KNNFIRST 已经验证 TTFT 维度的上限
  • Graph 验证 SWE-bench apply_ok 的上限
  • AST 验证覆盖率 + F1 的均衡上限
  • 三者并行部署（不同 mode 选不同路径）可能是实际系统的最优解
