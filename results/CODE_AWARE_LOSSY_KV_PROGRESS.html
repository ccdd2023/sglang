① 目标 & 支持的 regime

目标

  • Speed — TTFT 加速 vs prefix_cache_only / lossless baseline。
  • Accuracy — 同 prompt 下，精度不必差于通用（非 code-aware）复用算法。用 real token-F1 vs lossless 衡量。
  • 约束 — 加速只来自更多复用，不准用 KV-cache 调度 trick。

支持的 regime：KVCOMM 字节精确跨位置 copy + RoPE

同一 prompt 内容出现在不同绝对位置 → 拷贝 + RoPE delta（new_pos − old_pos）。AST chunking 是其上的编码专用优化（按函数/类粒度，部分变更的 slot 仍能复用未变函数）。

L3 MiniLM 语义 k-NN 不是这个 regime — 已弃用（research only）。复用闸门是字节精确文本匹配，AST 锚点只决定对齐边界，不做模糊匹配。

④ 测试 case 如何构造

giant-codebase benchmark（pandas / SWE-Smith）· --position-shift --partial-share --no-vary-code

① 数据源

SWE-Smith pandas manifest（results/giant_codebase/tasks/.../manifest.jsonl），每条 = 一个真实 pandas 任务：instance_id / patch / problem_statement / 涉及文件。

② 切片成 5 个 code_base slot

取 patch 涉及文件 + 同目录 sibling（--sibling-window 4），每个文件截断 8000 字符，前 5 个 = 5 个 slot。slot_id = code_base:<file path>（内容派生，非位置）。

③ 5 agent 固定角色链

implementer → debugger → reviewer → verifier → auditor

④ per-agent 变换

  • --position-shift：agent idx 按 (idx-1)%5 旋转 slot 顺序（同内容，不同绝对位置）。
  • --partial-share：AST 找顶层函数/类，每个 agent 丢 1 个不同函数（slot 文本不同，其余函数共享）。

⑤ 顺序执行 + cache_salt

agent 1 = source；agent 2..5 用不同 cache_salt → radix 冷 → 只能靠 KVCOMM 跨位置 copy + RoPE 复用。

⑤ giant-codebase 大 benchmark · 测试条件与多 agent 协作

真实 repo pandas-dev/pandas · SWE-Smith · 5-agent 角色链 · byte-exact KVCOMM regime · 驱动 bench_giant_codebase_reuse.py

① 测试条件

  • 真实仓库 pandas-dev/pandas：1502 个 .py 文件；SWE-Smith pandas 1000 任务池
  • 模型 Qwen2.5-7B-Instruct；持久 server（跨 case 复用池保留）
  • 每个 case = patch 涉及文件 + 同目录 sibling（--sibling-window 4）→ 切 5 个 code_base slot（每文件截 8000 字符）
  • fair A/B：同 case 跑 lossless（baseline，仅 radix 前缀）vs code-aware（KVCOMM 跨位置 copy+RoPE），同 prompt 同 seed
  • 速度指标 = reuser agent（2..5）的 TTFT；agent 1 (implementer) 是 source，不参与加速统计

② 多 agent 如何协作（顺序角色链 + upstream 交接）

一个 case 内 5 个 agent 顺序跑（非并行）：implementer→debugger→reviewer→verifier→auditor。

  • agent 1 = source：prompt 较短，其 code_base KV 入复用池。
  • agent 2..5 = reuser：各自用不同 cache_salt（giant:{case_id}:…:{idx}）→ radix 前缀冷 → 只能靠 KVCOMM 把池中跨位置的 code_base KV copy+RoPE 过来省 prefill（这是被测对象）。
  • 交接方式：每 agent 的 ## Upstream context 累加一句「{role} observed {N} cached tokens」—— 下游知道上游缓存命中，但看不到上游输出；各 agent 独立回一句「implementation risk」。

③ 多任务如何共享 KV（核心设计 · cross-task & cross-position 复用）

复用池的 key 是 内容派生的，与任务/位置/角色无关，所以同一个文件被多个任务/多个 agent 读取时，KV 自动跨边界共享。两条共享路径：

  • 跨 agent（同 case）：agent 2..5 旋转了 slot 顺序（同内容不同绝对位置）→ 旧的 positional key 会 miss；改用 slot_id = code_base:<file path> 后，同文件在任何位置都用同一个 pool key → 整 slot (L2) 或函数级 (L4) 字节精确匹配命中 → copy+RoPE 补位置差。
  • 跨 task（同 repo）：SWE-Smith 同一 patch 目录下的文件（如 pandas/core/interchange/*.py）在多个 task 重复出现 → 同 slot_id → 后续 task 命中前面 task 已入池的 KV。--sibling-window 4 刻意拉入同目录兄弟文件，正是为了制造这种跨任务 anchor 重叠。
  • 隔离边界：cache_salt 只隔离 radix 前缀缓存（让 reuser 的前缀冷、强制走 code-aware 路径）；它不隔离 code-aware 复用池 —— 池按 (slot_id, content_signature) 全局共享。server 全程不重启（--max-tasks 一次跑完），池跨 case 累积。
  • 命中条件：byte-exact —— slot 文本（L2）或函数签名+bytespan+tokenids（L4）必须完全一致才复用；AST 锚点只决定对齐边界，不做模糊匹配。partial-share 下整 slot 文本变（各丢 1 函数）→ L2 miss，但共享函数 L4 仍命中。

结论

  • 大模型同时放大加速与 F1（7B prefill ~2× 贵 → 复用省更多；coder 模型对 cross-context loss 更鲁棒）。
  • full-share 下 整 slot (L2) 在两轴都优于 AST (L4) — AST 的粒度在此是劣势（N 次拷贝 > 1 次），且 chunker 不带 fill 时漏掉模块级代码。

⑪ 已证 fundamental limit — Cross-Context KV Loss

Claim

非前缀 KV 复用（raw copy + RoPE）是 lossy 的，且 loss 随复用量单调增加。

Mechanism

layer > 0 的 KV 编码了它前面的 prefix。当一个 segment 在新 prefix 下被复用时，拷过去的 KV 是 stale 的 — 它是在不同的前文下算出来的。RoPE 只修位置，不修内容条件。

Evidence（7B-Coder, full-share position-shift）

复用量F1 vs lossless输出特征
~0 tok（lossless）1.000正确
~1400 tok（1 slot）0.461valid-but-different（切题但细节错）
~7100 tok（5 slots, MULTI_SLOT）0.000空白 / garbage

~52 置零的 inter-slot header tok 不是主因 — 7100 tok 的 stale slot KV 才是。single→multi 的单调崩坏即铁证。Radix (L1) 安全是因为它只复用相同前缀（同位置同前文）；每个非前缀层都某种程度 lossy。

⑫ 结论 & 唯一出路

SPEED · SOLVED

MULTI_SLOT 证明 code-aware 复用本身可给 7.5× TTFT 加速（97% 利用率）。速度 bar 达标。

ACCURACY · OPEN, 根因已证

大量 cross-context 复用（raw copy+RoPE）lossy：F1 0.46 → 0.00。这是 raw-copy+RoPE 的根本限制，不是 chunking/copy 机制的问题。

唯一出路：True CacheBlend

对每个拷贝的 chunk，在新 context 下重算 attention（而非 raw-copy + RoPE）。这是唯一能同时拿到速度与精度的机制。代价高（c2-fundamental-limits 的成本），尚未实现，待用户明确 sign-off。

Partial-share 仍是 AST chunking 有真实精度优势的 regime（F1 0.62 vs 0.51）— 可作 fallback/niche，但解不了大量复用的 loss。
