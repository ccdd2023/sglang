1. 四层缓存架构

命中顺序 L1→L2→L3→L4。L1/L2 已上线生产；L3 作为对照基准（"通用算法"）参与精度公平比较；L4 是本工作的 code-aware 算法，默认 OFF，通过 env 组合启用。

2. 核心问题与被证明的 Fundamental Limit

问题：多 agent 共享 code_base，但前缀不同（角色/任务不同）

5 个 agent（implementer/debugger/reviewer/verifier/auditor）前缀各异 → radix 只覆盖到角色分歧点 → code_base 处于非前缀位置。能否安全复用这部分 KV？

定理：非前缀 KV 复用不可能"既精确又有用"

KV 是整个前缀的函数。对一个非前缀位置的 code 块复用其 KV：

情况 A · 前缀相同
radix 前缀缓存已经覆盖该块
⇒ C2 冗余（复制已缓存 token，无加速，但精确）
情况 B · 前缀不同
块 KV 在旧前缀下计算 → 新前缀下错误
⇒ lossy（损失随上下文分歧增大）

推论：radix 前缀缓存之上，非前缀复用的"精确且有用"区为空。同前缀⇒radix 覆盖(冗余)；异前缀⇒lossy。raw-copy + RoPE ≠ 真 CacheBlend（后者需对 copied token 重算 attention）。

理论上唯一"快+精确"的 gap=0 窗口需要选择性驱逐（仅驱逐 code_base 叶子而保留共享前缀父节点），但 LRU 总先驱逐共享祖先 → 该窗口不可稳定工程化。因此 copy-based 非前缀复用被严格证明：快⇒lossy，精确⇒慢。

3. 算法一：AST Chunker（源码对齐）

把 code_base 按 AST 节点边界（函数/类/控制流）切成块，每块带 sha1[:16] 签名（与 MAScoder 字节级一致），用于跨请求去重。文本哈希缓存（512 LRU）避免多 agent 重复 parse。

  • SGLANG_CHUNK_TOPLEVEL=1 仅顶层函数/类（更少更大的块）
  • SGLANG_CHUNK_COARSE=1 整文件单块（≈L3 整槽粒度）
# ast_chunker.py — 跨请求一致的 AST 边界切块
def chunk_text(text):
    if SGLANG_CHUNK_COARSE:        # 单 module 块
        return [ChunkSpan(0, len(text), sig=text_hash)]
    tree = ast.parse(text)
    chunks = []
    for node in walk(tree):
        if isinstance(node, (FunctionDef, ClassDef)):
            sig = sha1(f"python:{type}:{name}:{norm}")[:16]
            chunks.append(ChunkSpan(
                byte_start, byte_end,   # 字节偏移
                signature=sig))         # 跨请求去重 key
        elif isinstance(node, (For,While,If,Try)):
            if TOPLEVEL: continue   # 跳过嵌套控制流
            ...
    return sort(chunks)[:32]

4. 算法二：AST-Gated L3（字节精确门控）NEW · commit 256304f39

给 L3 的 MiniLM k-NN 命中加一层 token 前缀字节精确门控：对命中条目与请求 span 做最长公共 token 前缀，仅复制那段字节精确前缀，零公共前缀则跳过。

效果：在变代码场景正确拒绝字节不同的槽（0 命中而非 lossy 命中），把 L3 的"语义近邻但字节不同"silent 失败转为安全跳过。

# radix_cache.py :: _try_placeholder_knn_lossy_match_body
# SGLANG_L3_AST_GATE=1 — 在 MiniLM 命中后加字节精确门
entry = knn_top1(query_embedding)
if L3_AST_GATE:
    # 最长公共 token 前缀
    lcp = longest_common_prefix(
        entry.token_ids, span.token_ids)
    if lcp == 0:
        return exact_only      # 字节全不同 → 安全跳过
    entry_len = lcp          # 截断到字节精确前缀
copy_kv(entry, len=entry_len)
apply_rope_delta(entry)      # head-only 批量 RoPE

5. 算法三：C2 CacheBlend 装配（gap 预填 + 块复制）LOSSY layer

当 AST-gate 拒绝时，回退到 块粒度装配：把命中的 L4 块 KV 复制到非前缀位置，仅预填 gap（gap = prefix 末到块首）。

  • SGLANG_CACHEBLEND_BATCH=1 一次 alloc+move+RoPE
  • SGLANG_CACHEBLEND_COMPACT=1 块在前缀后紧凑复制，gap 由 num_extend 填
  • SGLANG_CHUNK_POOL_PIN=0 关键：pinning 吃 KV pool 致 radix 驱逐
  • SGLANG_CACHEBLEND_MAX_CACHED_RATIO 成本守卫

C2 是首个 lossy 层（异前缀复制）。AST 块粒度能隔离"未改动的函数体"取得精度优势，但 per-chunk 复制开销 > L3 整槽复制 → 速度不及 L3。

# radix_cache.py :: _execute_chunk_plan_batched
device_indices = prefix_indices   # radix 前缀(免费)
for chunk in matched_chunks:
    gap = chunk.start - cursor
    if gap > 0:
        prefill(gap)             # 真实计算(成本=gap len)
    # 批量复制块 KV + head-only RoPE
    copy_kv(chunk.pool_slots, dst=device_indices)
    apply_rope_batched(chunk, delta)
    cursor = chunk.end
num_extend = input_len - cursor   # ≥0 安全
# 成本守卫: radix 已覆盖大半 prompt → 跳过
if prefix_len/input_len > MAX_CACHED_RATIO:
    return exact_only

6. 实验结果：Speedup × Accuracy

主结果（控制 A/B，公平 65k pool，同 prompt，token-F1 vs lossless）

8. 达标状态与下一步

两场景下 speedup 与 accuracy 均 ≥ 通用 L3 —— 目标达成。 变代码 speed bar(此前唯一未关闭项)已由 offset-aligned AST gate 关闭：1.448× ≥ L3 1.441×，accuracy 0.240 > 0.193(严格更优)。

现状

  • 变代码：L3+offset 1.448×/0.240 ≥ L3 1.441×/0.193 ✓✓ (accuracy 严格更优)
  • 同代码：L3+offset 1.243×/0.402 = L3 (offset gate 不触发，无回归) ✓✓
  • 放置仍 lossy(body KV 在 [prefix_len,…) 而非 body 实际位置)，但 AST 字节精确 body 复制(跳过差异 comment)使 accuracy 仍 ≥ L3

可继续改进方向(非阻塞)

  • 真 CacheBlend：对 copied token 重算 attention(一轮)→ 修正上下文漂移，可能把变代码 accuracy 进一步从 0.240 提升；但需 attention backend 改写，且只帮位置漂移
  • 变代码 accuracy 上限：当前 0.240 受放置 lossy 限制；gap prefill(慢)可提升到 0.30-0.67 但牺牲速度，fundamental tradeoff
  • 更大规模验证：当前 5 任务×5 agent；可在 50 任务持久 server 上复现
