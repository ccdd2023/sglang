\section{Evaluation}

We evaluate five research questions:
\begin{description}[leftmargin=*]
\item[RQ1] Does exact-content gating prevent unsafe reuse?
\item[RQ2] How close is RoPE-aligned reused KV to fresh KV?
\item[RQ3] Does exact-content reuse improve TTFT in prefill-dominated coding-agent settings?
\item[RQ4] Does exact-content segment reuse preserve downstream coding accuracy relative to lossless KV?
\item[RQ5] How much repo-level reuse opportunity exists at larger scale?
\end{description}

\subsection{Experimental Setup}

We use SWE-bench Verified and the SWE-bench Verified code-base-content dataset to construct repo-level cases with two to three large non-test Python files per case.
The 30-case pass@1 study first runs local base/gold smoke tests and then keeps the 28 cases where the gold patch passes and the base checkout has a nonzero target-test failure signal.
This filter avoids counting cases where the local test target is already solved or cannot be reproduced.
The main pass@1 comparison uses Qwen2.5-7B-Instruct with a constrained JSON-edit patch schema: the model emits file/search/replace edits, and the harness synthesizes a unified diff before running \texttt{git apply --check} and the local target tests.
Repo-level exact reuse and numerical ablations also include Qwen3-8B where noted.
All segment-reuse hits are required to report \exactgate.
All tables and data figures in this section are generated from local CSV/JSON artifacts by \texttt{paper/scripts/generate\_paper\_figures.py}; \texttt{paper/data\_manifest.json} records the exact source paths.

\subsection{RQ2: Numerical Correctness}

Correct RoPE delta alignment produces near-lossless behavior at the logit level.
Across the controlled ablation, correct delta reaches 0.999 mean K cosine, while large wrong deltas average 0.950.
The next-token KL divergence is 0.0147, top-1 agreement is 96.9\%, and top-5 overlap is 100\%.
This experiment isolates the numerical part of segment reuse from patch-generation quality: the same code span is reused across prompt positions, and variants differ only in whether the RoPE delta is correct, omitted, or intentionally wrong.

\subsection{RQ3: Performance}

\input{tables/table_ttft_stress}

\system's main performance question is whether exact-content code-segment reuse reduces streaming time-to-first-token (TTFT) when the workload is dominated by repeated repository-file prefill rather than decode.
Table~\ref{tab:ttft-stress} reports the 4090 TTFT-first micro/stress runs.
The benchmark uses \texttt{max\_tokens=1}, varies code length and agent count, and compares prefix-only caching against exact-content reuse plus code-base hints.
In the P0 sanity run, exact-content reuse plus hints reduces agent-level p50 TTFT from 246.9\,ms to 57.8\,ms, a 4.27$\times$ speedup; the corresponding p90 speedup is 6.44$\times$.
In the P1 8k single-segment shards, the p50 speedup is 5.10$\times$ for two agents and 4.24$\times$ for three agents.
These runs also keep output-token F1 at 1.0 against the prefix-only baseline.

The same table deliberately includes harder boundary rows.
With two 8k segments, or with 16k and 32k code blocks, exact-content signatures are still found, but the device-hit path is less stable and the p50/p90 TTFT gains shrink or disappear.
We therefore treat the 8k single-segment result as the current positive TTFT evidence and the longer-context rows as implementation-limit diagnostics, not as a claim of robust acceleration for every long-context prompt.

\input{tables/table_ablation}

Table~\ref{tab:ablation} isolates the 8k two-agent single-segment setting.
The ``Hints only'' row injects code-base hint metadata without enabling exact-content segment reuse and remains close to prefix-only.
The exact-content rows are the ones that produce large p50 gains and high cached-token counts, indicating that the repeated code object, rather than hint metadata alone, drives the best-case TTFT improvement.
However, the hints path still shows an incomplete consumed-counter signal: several requests report protected tokens or device hits without a matching consumed count.
We therefore present this table as fast-path evidence plus an implementation caveat, not as proof that all serving metadata paths are fully closed.

\input{tables/table_prefetch}

Table~\ref{tab:prefetch} is a realistic 100-case end-to-end serving check rather than the primary speedup claim.
The KVFlow baseline row uses the workflow-aware prefix-cache path from the reference implementation.
The ``Baseline + code hints'' row injects our code-base hint metadata without enabling exact-content segment reuse.
The final row enables both the hint path and exact-content reuse.
The current host storage backend is disabled in this run, so codebase prefetch queued tokens are zero.
Even so, combining codebase hints with exact-content segment reuse raises average cached tokens from 1{,}582 to 2{,}593 (a 64\% increase) relative to the prefix-only baseline, and records an exact-content hit for 99 of 100 cases.
Average end-to-end latency decreases only modestly, from 3{,}911\,ms to 3{,}838\,ms.
This small 100-case E2E speedup is expected: the run uses longer generated outputs and includes decode, HTTP, and scheduling overheads that dilute prefill savings.
We therefore use Table~\ref{tab:prefetch} as a realistic E2E serving sanity check, while Tables~\ref{tab:ttft-stress} and~\ref{tab:ablation} and Figures~\ref{fig:ttft-speedup} and~\ref{fig:agent-scaling} provide bounded TTFT-first evidence and expose the current fast-path limits.

\input{tables/table_graph_bundle_pass1}

The main pass@1 table compares lossless full-prefill KV and exact-content segment reuse on the same 28 local SWE-bench cases.
Lossless solves 3 cases; exact-content reuse solves 2.
The one-case delta is small relative to the low absolute pass@1 of this 7B constrained-patch setup.

\subsection{v44 placeholder\_knn\_lossy: Research-Direction Code Correctness}

The \texttt{placeholder\_knn\_lossy} mode is a research direction that extends the textually-identical exact-content reuse path (\S4) with a placeholder-anchored k-NN body that can reuse KV across \emph{cosine-similar} (not byte-identical) code spans. As of the v44 cycle (June 2026), it is a research prototype, not a production deployment; the production paths remain \texttt{lossless} and \texttt{exact\_reuse} (textually identical prefix match). This subsection summarizes the byte-equality correctness validation we ran on the research path, so that the reader can see that the v44 body does not regress downstream patch synthesis.

\textbf{Setup.} Per-case driver pattern: each SWE-bench case (or HumanEval task) runs in its own \texttt{sglang.launch\_server} process to bypass a pre-existing harness race in \texttt{RadixCache.\_delete\_leaf} (\texttt{python/sglang/srt/mem\_cache/radix\_cache.py:3858}), which is unrelated to v44 and out of scope for this paper. v44 mode is enabled via four environment variables:
\texttt{SGLANG\_PLACEHOLDER\_KNN\_MATCH=1},
\texttt{SGLANG\_PLACEHOLDER\_KNN\_PRE\_ROTATE\_DELTAS=1},
\texttt{SGLANG\_PLACEHOLDER\_KNN\_MIN\_COSINE=0.85},
\texttt{SGLANG\_PLACEHOLDER\_KNN\_TOPK=5}.

\textbf{Result.} Across 91 SWE-bench patches (10 cases Phase-2 + 27 stratified Phase-5 + 54 real Phase-3 FULL), \texttt{placeholder\_knn\_lossy} produces a patch byte-identical to the in-cell lossy baseline in every case. The pass@1 regression against the §6.5 two-percentage-point gate is \textbf{0pp}; the two cases that pass \texttt{git apply --check} (\texttt{psf\_\_requests-1142}, \texttt{scikit-learn\_\_scikit-learn-10297}) pass in both baseline and v44. Phase 3 also ran a 6-threshold (0.85/0.90/0.95/0.97/0.99/1.00) $\times$ K=5 sensitivity sweep using 3-cases-per-server chunks with the combined flags \texttt{--force-evict --disable-overlap-schedule --max-running-requests 1}; the 9 working cases produce byte-equal patches across all 6 thresholds (matplotlib case 3 crashed from the harness race; the 6 empty patches are filtered from the 54/54 real count). The §6.6 HumanEval-lite gate (10 tasks, \texttt{human\_eval.execution.check\_correctness}) records baseline pass@1 = 10\% (1/10) and v44 pass@1 = 10\% (1/10) with 10/10 byte-identical completion SHA; regression = +0.00\%. The §6.7 dense-prefill F1 gate (proxy: \texttt{prefix\_cache\_only} as closest non-anchor-reuse baseline) records \texttt{output\_token\_f1\_vs\_baseline} = 1.0000 across 25/25 (5 modes $\times$ 5 agent\_count) cells. The §6.8 F1-skip rate gate records 0.00\% in 25/25 cells.

\textbf{What the byte-equality result means.} The per-case driver starts a fresh \texttt{sglang} server per case, so the v44 \texttt{placeholder\_anchor\_pool} does not accumulate across cases. In this regime, \texttt{placeholder\_knn\_lossy} gracefully falls back to the textually-identical \texttt{lossy} path; the 0pp regression is therefore a \emph{fallback-invariance} test, not a direct exercise of the k-NN body. The k-NN body is exercised in the §6.7/§6.8 telemetry runs (\texttt{agent\_count=1..5}, \texttt{Qwen2.5-7B-Instruct}, \texttt{manifest\_500.json}), where the pool accumulates across 20 multi-agent runs; those runs report \texttt{F1=1.0000} and \texttt{sim\_mean $\geq$ 0.985} across all (mode, agent\_count) cells, indicating that high-similarity anchor matches do not change the model output distribution.

\textbf{Production status and limitations.} v44 is a research direction, not a production deployment. The production paths are \texttt{lossless} (no anchor reuse) and \texttt{exact\_reuse} (textually identical segment reuse), per the safety model in \S4. \texttt{placeholder\_anchor\_pool} is process-local and is not persisted across sglang server restarts. The 37 unique SWE-bench cases used in this validation is small for production claims; \texttt{Qwen2.5-3B-Instruct} is used, so 25/27 cases fail apply\_check because of model capability (not v44). Cross-model pass@1 (Llama/Mistral/32B) and a v10c-vs-v44 head-to-head comparison are deferred to follow-up work. The \texttt{\_delete\_leaf} harness race is a separate bug that limits multi-case-per-server to 3 cases; a proper fix would promote \texttt{RadixCache.write\_lock} to a top-level \texttt{threading.RLock}. The byte-equality result holds in both per-case and 3-cases-per-server setups, so the §6.5 0pp verdict is robust to the harness bug.

\subsection{RQ5: Scalability}

The 500-case manifest covers 12 real Python repositories and 1500 code segments.
It contains 5.97M source lines and about 58.8M reusable tokens.
The 100-case and 500-case gate statistics show that exact content signatures can be collected at scale, while preserving the same safety invariant used in the controlled and pass@1 runs.
The 500-case manifest contains 681 unique content signatures, indicating both substantial repetition and enough diversity to exercise the locator and signature pipeline beyond a small hand-picked suite.
