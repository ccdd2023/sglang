## 2. 关键分歧裁决：capacity fallback reason

### 直接证据

`p6delta-s0-rho2-chunk4096-r0.json`的40次fallback仅保存：

```text
request_outcomes.dense_fallback = 1
reservation_failures = 0
cached_tokens = 64
outcome = dense_fallback
```

顶层为：

```text
approximate_recovery_failed_dense = 40
terminal_reason_counts = {}
```

capacity raw及两个capacity server log中均不存在：

- `store_miss`
- `terminal_reason_observations`
- reason-labelled Prometheus样本

runner行为：

1. `run_p6_4_capacity_pilot.py:484-493`临时获取完整Prometheus文本；
2. `:497-519`只提取`approx_kv_requests_total`的outcome；
3. `:543`只持久化`request_outcomes`；
4. `:605-610`通过`metric_snapshot`仅保存合并后的fallback token数；
5. `metrics.py:63`按metric name聚合，丢弃`reason` label；
6. 可保留reason的`terminal_reason_observations()`并未被capacity runner调用。

相比之下，W/R4 raw确实保存：

```json
{
  "raw": {"store_miss": 1024},
  "mapped_from": {"unsupported": ["store_miss"]},
  "verification": "direct"
}
```

### 裁决

- **拒绝**Opus的“所有fallback raw reason均为store_miss”作为全局结论。
- 准确说法是：**所有已持久化的W/R4 fallback reasons均为store_miss；capacity S0的40次reason未持久化。**
- 根据注册成功、approx eviction、零reservation failure及runtime路径，`store_miss`是高度可信推断，但不是raw中的直接证据。
- 无法通过现有raw/log精确离线恢复每请求reason。

### GPU结论

为严格满足V7“每次approximate failure恰有一个exclusive reason”的合同，需要：

- capacity runner保存reason-labelled observation；
- 最少执行1个`p6delta-s0-rho2-chunk4096` correction start。

若治理要求新code pin下wave0保持完整配对，则运行S0/S4共2 starts。无需重跑A8、W或R4。

唯一免GPU方案是主会话明确接受post-hoc waiver，并将capacity reason标记为`inferred/not_directly_recorded`，同时撤回“terminal taxonomy完整”的claim；这不满足原冻结合同。
